Add an opt-in soft delete mode to "base" collections, so that deleting a record moves it into a trash it can later be restored from instead of removing its row.

The mode is off by default and is turned on per collection through a `softDelete` boolean in the collection options, next to a `trashRetention` integer holding the number of seconds after which a trashed record expires. Zero retention keeps trashed records forever, and setting a non-zero retention while the mode is off has to be rejected as a validation error. A collection that does not enable the mode must keep behaving exactly as it does today, right down to its serialized JSON and its exported database row: no extra keys, no extra fields, no extra indexes. While the mode is on the collection carries a system date field named `deleted` holding the moment the record was trashed, and turning the mode off takes it away again. Enabling the mode leaves the existing records untouched and visible, and so does disabling it. That value is managed internally, so it must be ignored when a client sends it in a record create or update body, and if the collection already has a field called `deleted` that is not a date field then enabling the mode should be rejected too.

Deleting a record of such a collection stamps that timestamp rather than removing the row, and the usual record delete hooks still run around it. Deleting a record that is already in the trash removes it for good, and `App.PurgeRecord` together with a context-taking variant does the same for a record that is still live. Both of those permanent paths keep the cascade behavior that already exists for referencing records — including referencing records that are themselves in the trash — and everything they cascade into is removed permanently as well.

A record sitting in the trash has to be invisible to every ordinary read path: the record queries and all the finders built on them, the list and view endpoints, and the relation, back-relation and `@collection` filters. Expanding a relation that points at a trashed record yields nothing. Reaching the trash requires asking for it explicitly, through `App.RecordQueryWithTrashed` for live and trashed records together, `App.TrashedRecordQuery` for only the trashed ones (which matches nothing on a collection without the mode), and `App.FindRecordByIdWithTrashed`, `App.FindTrashedRecordById` and `App.FindAllTrashedRecords` for the corresponding lookups; the last two should report an error when the collection does not have the mode enabled. A record can be asked whether it is trashed and when, through `IsTrashed` and `TrashedAt`, and a trashed record cannot be edited — a validating save of one has to fail, while the saves that skip validation stay allowed because that is the internal path.

Because a trashed row is still physically in the table it would otherwise keep reserving its unique values and block a new record with the same data, so while the mode is on the collection's unique indexes have to stop counting the trashed rows, and turning the mode off has to give back exactly the index expressions the collection had before. The consequence to get right is that once a record is trashed another record may claim its unique value, and restoring the trashed one then has to fail.

Trashing a record also moves into the trash the records that reference it through a cascade-delete relation, recursively, but it leaves the relation values themselves alone since the record is still there and may come back. A referencing record whose relation holds several values follows the main record only when the trashed record is the last reference it has left. Everything trashed by a single delete shares one timestamp, and two separate delete operations must never end up sharing one, because that group is exactly what `App.RestoreRecord` and its context-taking variant bring back: the record plus the records that went into the trash with it, while a record that had been trashed on its own earlier stays there. Restoring a record that is not trashed is a no-op, restoring one from a collection without the mode is an error, and a record cannot be restored while a record it cascade-depends on is still in the trash.

Emptying the trash from Go goes through `App.PurgeTrashedRecords`, which permanently deletes the trashed records of a collection that were trashed before a given time and returns how many it purged, treating a zero time as the whole trash and a collection without the mode as an error. `App.PurgeExpiredTrashedRecords` applies each collection's own retention and skips the ones that have none, and expired records should also be purged periodically in the background.

Over HTTP, the record list and view endpoints take a `trashed` query parameter, where `with` returns live and trashed records together, `only` returns just the trashed ones, an empty value keeps the current behavior and anything else is a 400; on a collection without the mode the parameter is accepted and does nothing. The record delete endpoint takes a `purge` parameter, where a truthy value deletes the record permanently and also finds a record that is already in the trash, and a non-boolean value is a 400. Restoring is a POST to `/api/collections/{collection}/records/{id}/restore`, guarded by the collection's update rule and responding with the restored record; a record that is not in the trash is a 404 there and a collection without the mode is a 400.

Finally, a DELETE to `/api/collections/{collection}/trash` empties a collection's trash and responds with the number of records it purged under a `purged` key, accepting an optional `before` datetime query parameter to spare the more recently trashed ones. Since it is a bulk irreversible operation it is restricted to superusers, and a collection without the mode is a 400.
