Add an opt-in soft delete mode to "base" collections: deleting a record moves it into a trash it can later be restored from, instead of removing its row.

A `softDelete` boolean in the collection options turns the mode on per collection, beside a `trashRetention` integer of seconds after which a trashed record expires. Zero keeps them forever, and a non-zero retention while the mode is off is a validation error. While on, the collection carries a system date field named `deleted` holding when the record was trashed; turning the mode off removes it, and `softDelete` appears in the serialized options only when on. Toggling either way leaves existing records untouched and visible. Enabling is rejected if a non-date `deleted` field already exists.

Deleting a record already in the trash removes it for good, as does `App.PurgeRecord` on a live one. Both permanent paths keep the existing cascade for referencing records, trashed ones included, cascading permanently.

Trashed records must be invisible to every ordinary read path, relation, back-relation and `@collection` filters included; expanding a relation pointing at one yields nothing. Reaching them takes `App.FindRecordByIdWithTrashed`, `App.FindTrashedRecordById` and `App.FindAllTrashedRecords`, the last two erroring without the mode. Records report `IsTrashed` and `TrashedAt`, and saving a trashed record must fail validation.

A trashed row still reserves its unique values, so while the mode is on the collection's unique indexes must stop counting trashed rows, and turning it off must give back exactly the previous index expressions. Another record may then claim a trashed record's unique value, and restoring the trashed one has to fail.

Trashing also trashes the records referencing it through a cascade-delete relation, recursively, leaving relation values alone. A referencing record holding several values follows only when the trashed record is the last visible one it points at. Everything trashed by one delete shares a timestamp, and separate deletes must never share one, because `App.RestoreRecord` brings back exactly that group; a record trashed earlier on its own stays. Restoring an untrashed record is a no-op, restoring without the mode is an error, and a record cannot be restored while a record it cascade-depends on is still trashed.

`App.PurgeTrashedRecords` deletes a collection's records trashed before a given time and returns the count, treating a zero time as the whole trash and a collection without the mode as an error. `App.PurgeExpiredTrashedRecords` applies each collection's retention and skips those without one.

Over HTTP the list and view endpoints take a `trashed` parameter: `with` returns both, `only` returns just trashed, empty keeps today's behavior, anything else is a 400; without the mode it does nothing. The delete endpoint takes `purge`, where a truthy value deletes permanently and also finds an already trashed record; a non-boolean is a 400. `POST /api/collections/{collection}/records/{id}/restore` restores under the update rule and returns the record, 404 when not trashed and 400 without the mode. `DELETE /api/collections/{collection}/trash` is superuser-only, reports the count under `purged`, takes an optional `before` datetime, and is a 400 without the mode.
