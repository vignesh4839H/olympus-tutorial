Add an opt-in soft delete mode to "base" collections. Deleting a record should move it to a trash you can restore from.

Turn it on per collection with a `softDelete` boolean, alongside `trashRetention`, seconds until a trashed record expires; zero keeps it forever. Setting a retention while the mode is off is a validation error. With the mode on the collection grows a system date field called `deleted` holding when the record was trashed, and loses it when the mode goes off. Anything a client sends for `deleted` in a record body is ignored. The option itself shows up in the serialized options only while it is on. Flipping the switch either way must not disturb the records already there. If the collection defines its own `deleted` field, refuse to enable.

Deleting an already trashed record permanently removes it. `App.PurgeRecord` skips the trash entirely and does the same to a live one. Both pull in the referencing records, trashed ones included, and everything they reach goes permanently.

Trashed records stay out of the ordinary read paths, including relation, back-relation and `@collection` filters, and expanding a relation onto one gives back nothing. To reach them: `App.FindRecordByIdWithTrashed`, `App.FindTrashedRecordById`, `App.FindAllTrashedRecords`. The last two error without the mode. Records answer `IsTrashed` and `TrashedAt`, and saving one that is trashed must fail validation.

With the mode on the collection's unique indexes must stop counting trashed rows, though the index text the collection reports stays exactly as it was written; turning it off must give back exactly the expressions it had before.

Records pointing at a trashed record through a cascade-delete relation go too, recursively, though their relation values stay put. Where a relation holds several values, the referencing record follows only if the trashed record was the last visible thing it pointed at. Everything caught by a single delete shares one timestamp, and two separate deletes must never share one, because that group is what `App.RestoreRecord` brings back. Restoring an untrashed record does nothing, restoring without the mode is an error, and nothing can be restored while something it cascade-depends on is still trashed. The record handed to `App.RestoreRecord` comes back live in place, so that same instance can be changed and saved straight afterwards.

`App.PurgeTrashedRecords` clears a collection's records trashed before a `types.DateTime` cutoff and reports how many went. Pass the zero value to empty the lot. A collection without the mode is an error. `App.PurgeExpiredTrashedRecords` applies each collection's retention, skipping any without one.

Over HTTP, list and view take `trashed`: `with` for both, `only` for just the trashed, anything else a 400; without the mode it does nothing. Delete takes `purge`: a true value deletes permanently, and a non-boolean is a 400. `POST /api/collections/{collection}/records/{id}/restore` goes through the collection update rule and answers with the restored record the way an update does, 404 if it was not trashed, 400 without the mode. `DELETE /api/collections/{collection}/trash` is superusers only, reports the count under `purged`, takes an optional `before` datetime, and is a 400 without the mode.
