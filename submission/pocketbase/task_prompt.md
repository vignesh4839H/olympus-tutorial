Add an opt-in soft delete mode to "base" collections, so deleting a record moves it to a restorable trash.

Turn it on per collection with a `softDelete` boolean, alongside `trashRetention`, seconds until a trashed record expires; zero keeps it forever. A retention with the mode off is a validation error. With the mode on the collection grows a system date field `deleted` holding when the record was trashed, and loses it when off. Anything a client sends for `deleted` is ignored. The option shows up in the serialized options only while on. Flipping the switch either way must not disturb existing records. If the collection defines its own `deleted` field, refuse to enable.

Calling `App.Delete` on an already trashed record permanently removes it. `App.PurgeRecord` does the same to a live one, skipping the trash. A second delete and `App.PurgeRecord` permanently delete the referencing records too, including ones already in the trash, recursively.

Trashed records stay out of ordinary read paths, including relation, back-relation and `@collection` filters, and expanding a relation onto one gives nothing. To reach them: `App.FindRecordByIdWithTrashed`, `App.FindTrashedRecordById`, `App.FindAllTrashedRecords`. The last two error without the mode. Records answer `IsTrashed` and `TrashedAt`, and saving a trashed one must fail validation.

With the mode on, unique indexes must stop counting trashed rows, though the index text the collection reports stays exactly as written; turning it off gives back exactly the earlier expressions.

Records pointing at a trashed record through a cascade-delete relation follow it, recursively. Trashing leaves every stored reference alone, cascading or not, unlike a permanent delete, so a restore brings the old filter matches back. Where a relation holds several values, the referencing record follows only if the trashed one was its last visible target. All records trashed by one delete share a timestamp, and separate deletes must never share one; `App.RestoreRecord` uses that group to bring them back. Restoring an untrashed record does nothing, restoring without the mode errors, and nothing can be restored while something it cascade-depends on is still trashed. The record handed to `App.RestoreRecord` comes back live in place, so that instance can be changed and saved again.

`App.PurgeTrashedRecords` clears a collection's records trashed before a `types.DateTime` cutoff and reports how many went. The zero value empties the lot; a collection without the mode errors. `App.PurgeExpiredTrashedRecords` applies each collection's retention, skipping those without one.

Over HTTP, list and view take `trashed`: `with` for both, `only` for just the trashed, anything else a 400; without the mode it does nothing. The delete endpoint takes a boolean `purge`; `true` permanently deletes the record, a non-boolean returns 400, and without it the route only reaches live records, so a trashed id is a 404. `POST /api/collections/{collection}/records/{id}/restore` goes through the collection update rule and answers with the restored record as an update does, 404 if it was not trashed, 400 without the mode. `DELETE /api/collections/{collection}/trash` is superusers only, reports the count under `purged`, takes an optional `before` datetime, and is a 400 without the mode.
