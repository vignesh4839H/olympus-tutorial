Add an opt-in soft delete mode to "base" collections: deleting moves a record to a restorable trash.

Turn it on per collection with a `softDelete` boolean and a `trashRetention` in seconds; zero keeps trash forever, a retention with the mode off invalid. The mode adds a system date field `deleted` recording when the record was trashed, and drops it when off. A client value for `deleted` is ignored, though the field still appears in the API record, empty while live. The option is serialized only while on. Toggling must not disturb existing records; with the field gone the trashed ones read as live again. A collection with its own `deleted` field refuses to enable.

`App.Delete` on an already trashed record permanently removes it, and `App.PurgeRecord` does that to a live one. Both reach referencing records too, already trashed ones included, recursively.

Trashed records stay out of ordinary reads, including relation, back-relation and `@collection` filters; expanding a relation onto one gives nothing. A filter naming a relation misses a trashed target however spelled, `rel` as well as `rel.id`. Reach them with `App.FindRecordByIdWithTrashed`, `App.FindTrashedRecordById` and `App.FindAllTrashedRecords`; the last two error without the mode. Records answer `IsTrashed` and `TrashedAt`, and saving a trashed one fails validation.

While on, unique indexes stop counting trashed rows, though the index text the collection reports stays exactly as written; turning it off gives the earlier expressions back.

Records reaching a trashed record through a cascade-delete relation follow it, recursively, though trashing leaves every stored reference alone, cascading or not, so a restore brings the old matches back. A multi-value relation follows only if the trashed one was its last visible target. One delete stamps one timestamp, separate deletes never share one, and `App.RestoreRecord` brings that group back from the record the delete started at. Restoring an untrashed record does nothing, restoring without the mode errors, and nothing restores while something it cascade-depends on is still trashed, even within one group. The record it is handed comes back live in place, ready to change and save.

`App.PurgeTrashedRecords` clears records trashed before a `types.DateTime` cutoff and reports how many went; the zero value empties the lot, and a collection without the mode errors. `App.PurgeExpiredTrashedRecords` applies each collection's retention, skipping those without one.

List and view accept `trashed`: `with` returns live and trashed, `only` just the trashed, anything else a 400; without the mode it does nothing. The batch endpoint accepts the restore action too. Delete takes a boolean `purge`: `true` removes the record permanently, a non-boolean returns 400, and without it the route reaches only live records, so a trashed id is a 404. `POST /api/collections/{collection}/records/{id}/restore` goes through the collection update rule and answers with the restored record: 403 when the rule is nil, 404 when it does not match or was not trashed, 400 without the mode. `DELETE /api/collections/{collection}/trash` is superusers only, answers 401 to a guest, reports the count under `purged`, and takes an optional `before` datetime, a 400 when malformed or without the mode.
