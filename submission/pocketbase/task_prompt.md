Add an opt-in soft delete mode to "base" collections: deleting a record moves it to a restorable trash.

Turn it on per collection with a `softDelete` boolean and a `trashRetention` in seconds; zero keeps the trash forever. A retention with the mode off is invalid. With the mode on the collection grows a system date field `deleted` holding when the record was trashed, and loses it when off. Anything a client sends for `deleted` is ignored, though it still appears in the API record, empty while the record is live. The option is serialized only while on. Flipping the switch either way must not disturb existing records; with the field gone the trashed ones read as live again. If the collection defines its own `deleted` field, refuse to enable.

Calling `App.Delete` on an already trashed record permanently removes it. `App.PurgeRecord` permanently deletes a live one, skipping the trash. Both reach the referencing records too, already trashed ones included, recursively.

Trashed records stay out of ordinary reads, including relation, back-relation and `@collection` filters, and expanding a relation onto one gives nothing. A filter naming a relation misses a trashed target however it is spelled, `rel` as well as `rel.id`. To reach them: `App.FindRecordByIdWithTrashed`, `App.FindTrashedRecordById`, `App.FindAllTrashedRecords`. The last two error without the mode. Records answer `IsTrashed` and `TrashedAt`, and saving a trashed one fails validation.

With the mode on, unique indexes stop counting trashed rows, though the index text the collection reports stays exactly as written; turning it off gives the earlier expressions back.

Records pointing at a trashed record through a cascade-delete relation follow it, recursively. Trashing leaves every stored reference alone, cascading or not, so a restore brings the old filter matches back. Where a relation holds several values, it follows only if the trashed one was its last visible target. All records trashed by one delete share a timestamp, and separate deletes must never share one; `App.RestoreRecord` brings that group back. Restoring an untrashed record does nothing, restoring without the mode errors, and nothing can be restored while something it cascade-depends on is still trashed, even when both went in together; the group comes back from the record the delete started at. The record it is handed comes back live in place, ready to be changed and saved again.

`App.PurgeTrashedRecords` clears the records trashed before a `types.DateTime` cutoff and reports how many went. The zero value empties the lot; a collection without the mode errors. `App.PurgeExpiredTrashedRecords` applies each collection's retention, skipping those without one.

List and view accept a `trashed` query parameter: `with` returns live and trashed records, `only` just the trashed ones, any other value a 400. Without the mode the parameter does nothing. The batch endpoint accepts the restore action too. The delete endpoint takes a boolean `purge`: `true` permanently deletes the record, a non-boolean returns 400, and without it the route reaches only live records, so a trashed id is a 404. `POST /api/collections/{collection}/records/{id}/restore` goes through the collection update rule and answers with the restored record: 403 when the rule is nil, 404 when it does not match or the record was not trashed, 400 without the mode. `DELETE /api/collections/{collection}/trash` is superusers only, answers 401 to a guest, reports the count under `purged`, takes an optional `before` datetime that is a 400 when malformed, and a 400 without the mode.
